## 1. 分析与交付

| 交付单元 | 原有问题 / 边界 | 本次实现 |
| --- | --- | --- |
| N1-01 任务契约与持久化 | 运行正常结束不能证明目标完成；无独立任务领域 | 稳定任务/步骤/条件 ID、依赖、阻塞原因、计划与条件修订；独立原子任务存储、CAS、幂等、恢复与明确续接 |
| N1-02 状态快照与重同步 | 原有请求序号和 80ms 通知合并不足以覆盖服务端重启或丢失终态 | host epoch、快照修订/事件序号、run/worker 身份；丢失/乱序重取、可见性/联网恢复、运行中每 5 秒有界兜底读取 |
| N1-03 计划工具与界面 | 宿主工作流不等于模型管理任务步骤 | `update_plan` / `read_task`；步骤、条件、阻塞、历史修订和明确继续入口；简单问答保持无计划 |
| N1-04 验证证据与摘要 | 模型声明或退出码 0 容易被误读为验收通过 | 宿主命令回执、工作区内容指纹、任务期间变更摘要、逐条件人工核验和整体确认；文件/计划/条件变化使证据过期 |

四个单元按文件归属并行开发，关键变更分别提交，最终作为一个 N1 集成候选验证完整链路。可选工作流验收门槛仍属于后续独立扩展，不改既有工作流的默认推进条件。

## 2. 使用方式

1. 显式选择 Native 会话并配置可用模型连接。复杂任务可让模型使用 `update_plan` 创建步骤与验收条件；工具按宿主绑定的当前任务操作，不能通过参数选择别的会话。
2. “Native 任务”面板分别显示运行结果、模型实现声明和验收状态。写文件、执行命令与 MCP 的既有审批仍有效，更新计划不批准其他操作。
3. 查看步骤、阻塞原因、命令/退出码/输出、扫描范围内的文件变化。成功命令仍是待核验的证据，不自动证明验收条件满足。
4. 本轮结束后，在“人工核验与任务验收”中逐项确认通过、失败或不适用，并填写理由。所有步骤声明实现、所有条件有当前版本的人工核验后，才能确认整个任务验收。
5. 点击“继续此任务”只将该任务关联到下一条待发送消息；用户仍需自行发送。关联进入队列持久记录和提交去重摘要；普通新消息不自动接管旧任务。
6. 刷新失败显示“状态未知”和重试入口。连续两次读取失败暂停自动重试；重新聚焦、联网或手动重试可恢复同步。旧任务与新一轮无计划问答分开展示。

纯分析或文档任务可使用人工检查条件；不需要伪造自动测试。所有条件均经明确确认不适用时显示“不适用”，不会显示自动测试通过。

## 3. 状态和兼容约束

- `RunStatus` / `ChatTurnResult.success` 的运行语义保持不变。队列仍按实际运行回执确认，工作流仍按既有规则推进；“未验收”不转换成 `success=false`。
- 模型只能提出计划、条件和实现进度。命令证据来源是已持久化的真实工具结果；成功回执保持 `unverified`，失败回执为 `failed`。stdout 中的 PASS、模型最终回答或 MCP 返回成功均不能直接创建验收通过。
- 整体验收需要当前人工条件证据、全部步骤实现和明确的整体确认。宿主再次校验条件，不能绕过按钮禁用调用 IPC 强行通过。
- 任务记录与原运行日志独立。旧会话没有任务文件时正常读取；重启从运行日志核对任务是否结束或中断，不自动重放工具。模型上下文压缩不删除独立任务记录，可用 `read_task` 恢复索引。
- 通用聊天快照增加可选字段，Claude 继续可用；native 完成通知改为“本轮执行已结束”。快照还携带宿主会话状态，避免 workspace 终态事件丢失后一直显示 stopping。
- 跨回合延续必须经用户选择，绑定当前任务及原 run；相同 requestId 改变关联任务会被拒绝。来自旧 worker、旧修订或其他会话的更新不能覆盖新状态。

## 4. 证据与工作区范围

宿主在首次计划或本轮首次副作用工具执行前建立基线，因此先编辑后补计划也能保留原始用户内容的基线。后续以实际文件字节、权限和根目录身份生成指纹，不仅比较 Git HEAD。任务变化表示“任务期间观察到”，不能据此断言全部改动都由 Agent 产生，也不能直接作为回滚清单。

默认扫描最多 4000 项、总计 32 MiB、单文件 4 MiB、5 秒。排除 `.git`、`node_modules`、`dist`、`release`、`.next`、`coverage`、敏感路径和宿主保护目录。界面显示范围和不完整原因；符号链接、超限、扫描期间变化等均不能冒充完整现场。扫描只读取内容用于摘要，不持久化文件正文。

命令证据包含实际工具调用 ID、程序/argv/cwd、退出码、日志摘要、截断标志、输出摘要及计划/条件/工作区版本。日志展示上限 8192 字节，缺失和截断明确标记；费用用量缺失不否定真实功能证据。

更新计划、修改验收条件、工作区发生改变或扫描变得不完整时，相关证据失效。人工核验保存前再次检查现场指纹，避免在旧界面上确认已变化的代码。外部文件变化在宿主刷新或复核时重新检查；此机制不是操作系统文件锁，也不承诺原子冻结外部编辑器。

IPC 使用精简任务视图，不重复发送基线/当前两份最多 4000 文件的哈希库存；完整清单只在宿主持久记录中保存。当前版本不裁剪证据与计划历史。

## 5. 持久化与失败处理

任务记录位于应用数据目录的 `native/tasks/<conversationId>/tasks.json`，原始 native 运行账本不迁移。任务存储采用单写入锁、严格 schema/身份校验、内容校验和、临时文件、fsync 与原子替换；错误不会删除旧记录。

每个会话最多保存 16 个计划任务；每任务最多 256 条证据、512 次修订，任务文件最多 16 MiB。模型工具将单个计划限制为 32 步、32 条条件，读取证据/历史索引采用有界分页。达到上限明确拒绝，不静默删历史；必要时新建会话继续。暂不提供任务归档/清理界面。

- 计划提交无法确认时，工具返回未知结果并停止后续自动执行；不能展示未落盘的计划已保存。
- 工具/运行回执已落盘后，附加证据观察失败单独显示任务状态未知，不把已完成运行改为失败队列项。重新读取记录可以修复元数据，不能重做原工具。
- 元数据 writer 关闭失败保留实例和资源屏障，显式停止或退出时重试释放；只重试释放，不启动新 worker。已持久化的执行成功仍可确认。
- 人工复核绑定修订与现场指纹，并经过可信 renderer/main-frame IPC、会话和目录维护边界；取消、归档、维护或身份变化会拒绝旧操作。
- 降级前先停止所有运行并保留应用数据备份。旧版本不展示或维护 N1 任务状态，不能用旧版的完成文案替代 N1 验收；回到支持 N1 的版本后重新核对任务现场。
