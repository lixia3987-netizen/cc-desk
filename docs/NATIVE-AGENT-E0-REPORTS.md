## 1. 版本与交付范围

原有 `scripts/native-eval.mjs prepare / verify / compare` 三个小任务的有效用法保持。新命令使用 `engineering-` 前缀，并验证固定的工程套件身份：

| 项目 | 固定值或含义 |
| --- | --- |
| suiteId | `cc-desk-engineering-v1` |
| taskBaseline | `b45bd0623d2a44a2878c46d4701fa4b388c7d9be` |
| suiteDigest | `7ac65759b84e3946f632a931ff7bece2e50051fc25b2ee9a5e0c23bd2cbfba8a` |
| appRevision | 操作者预先指定的完整应用 commit；与任务代码基线分开，脚本不自动识别实际运行的桌面二进制 |
| 批次 | Native / Claude × 三项任务 × 第 1 / 2 轮，共 12 条固定记录 |
| 验收尝试 | 同一轮可以多次运行代码检查，每次保存新的意图和结果；不覆盖此前失败 |

v1 材料目录保持原样，包括原模板和历史 `validation.json`；摘要按原规则排除派生的 `validation.json`。不支持通过改写旧版本材料绕过摘要检查。报告自身使用独立 `kind` 与 `schemaVersion`，旧 smoke 报告不能混入工程对照。

## 2. 准备记录与任务现场

从评估者仓库执行，先选择全新、位于评估者与候选项目之外的操作者目录：

```sh
node scripts/native-eval.mjs engineering-init /absolute/e0-batch <完整应用commit>
```

生成 `manifest.json`、`records/` 下的 12 条记录和 `attempts/` 目录。非空目录拒绝初始化，已有记录不会被覆盖。所有未知用量、费用、预算、耗时及介入次数保持 `null`，真实质量、图形和平台验收保持 `pending`。

任务项目仍按 [E0-01 隔离准备步骤](NATIVE-AGENT-E0.md#3-材料隔离与现场准备)创建：每个引擎/任务/轮次使用独立副本，固定任务基线，只放入对应 `TASK.md` 和必要缺陷注入。不要把验收器或参考实现交给被评估 Agent。新命令不克隆、不联网安装依赖、不执行模型请求。

编辑对应 `records/<runId>.json`，记录实际服务、模型、协议、配置引用、凭据来源引用、预算、模型运行状态与证据位置。记录中只放引用，不写凭据值。模型失败、取消、预算耗尽或环境错误不能因之后代码检查通过而改称成功；重跑或补充人工救援要保留原记录证据和历史报告。

`appRevision`、配置、真实服务证据和人工复核引用属于操作者声明。脚本不会验证账号、调用服务、读取引用指向的私密资料，也不会由 `manual-real` 或人工复核引用自动生成正式通过结论。

## 3. 受控独立验收

评估者需要已经安装固定依赖并构建本地包（`npm run build:packages`），候选也需要可用的固定依赖和指向自身包的 workspace 链接，具体沿用 E0-01。不要让候选错误地导入评估者工作区的包编译结果。

```sh
node scripts/native-eval.mjs engineering-verify /absolute/e0-batch native-01-snapshot-refresh-r1 /absolute/e0-native-r1-refresh
node scripts/native-eval.mjs engineering-verify /absolute/e0-batch native-01-snapshot-refresh-r1 /absolute/e0-native-r1-refresh --timeout-ms 120000
```

每次先持久保存独立的 `intent.json`，绑定套件、记录快照、候选目录、时限与尝试 ID，然后执行评估者固定的验收逻辑。结果写入同一次尝试的全新 `result.json`；任何已有结果都不能被替换。缺少结果的意图作为未知尝试保留，不自动续跑。

验收运行在受控子进程，复用现有 ProcessSupervisor 的进程树收束能力。验收子进程默认执行时限 120 秒，可指定 1–300000 毫秒；前后 Git/源文件检查另受命令时间、文件数和字节限制；共享输出预算 256 KiB，截断输出不能形成通过结果。输出必须具有完整的正确任务回执，并与退出码一致；单独输出“通过”、无回执退出 0、超时、取消或清理未确认均不能计为通过。

独立检查前后检查源文件版本，并在原测试及新增测试执行后再次验证保护文件。源码/HEAD 在验收期间变化会阻止通过。快照范围是基线文件、当前 tracked 文件和 Git 未忽略的 untracked 文件，受文件数和字节预算限制；依赖及被 Git 忽略的构建输出不属于完整目录审计。检查不能证明操作系统隔离，也不抵御任意恶意候选对评估者进程的攻击，正式验收仍使用独立账号或临时容器。

同一批次通过独占锁串行验收。清理未确认、崩溃或结果无法持久保存时保留阻断；不得直接重复执行。操作者须先检查进程和候选现场，再处理遗留锁。不同批次不能并发复用同一候选；不同轮次及引擎必须使用独立任务项目。

自动检查结果仅表示该次指定 oracle、保护规则、四包编译和选定原/新测试的实际结果。它与模型运行状态、真实质量认可、图形验收和成品验收分别记录。CLI 自动检查通过退出 0，检查未通过退出 1，参数或准备错误退出 2。

## 4. 汇总与比较

```sh
node scripts/native-eval.mjs engineering-report /absolute/e0-batch /absolute/e0-reports/report-01.json
node scripts/native-eval.mjs engineering-compare /absolute/e0-reports/report-01.json /absolute/e0-reports/report-02.json
```

报告文件必须新建；后续更新使用新文件名。报告始终包含完整的 12 条计划记录，未验收项明确列出。每次已记录的尝试均保留，包含失败、超时、取消、异常以及有意图无结果的未知状态，不只选最后一次绿色结果。原始日志仍保存在各尝试结果中，汇总保留摘要、哈希和相对引用。

汇总分别统计操作者声明的模型状态与实际自动验收状态。指标来自当前 12 条运行记录，保留每次尝试的记录快照；重复验收不重复累加成模型调用或费用。已发生的模型失败须先保存对应证据/记录快照，工具不能发现目录之外未登记或被人工删除的历史。

未知数与零区分，汇总带已知数量、总数量和完整性。用量缺失时不生成完整 token/费用总量；币种不同不相加为可比较金额。对照重新验证套件、固定轮次和摘要，披露应用、模型、协议、配置和预算差异；不自动宣布引擎优胜或估算通用成功率。可携带报告中的证据引用不等于重新读取并认证外部原始日志。

本版每批最多 120 次验收尝试；单次模型运行记录最多 16 KiB，单条 JSON 文件最大 1 MiB，报告最大 8 MiB。超限、损坏、重复或身份不匹配的记录明确拒绝，不通过忽略它们来生成较小的成功分母。
