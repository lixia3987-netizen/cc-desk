## 1. 决策与范围

下一轮优先让单 Agent 可靠完成真实工程任务：先补齐任务计划、可信状态和验证证据，再改进代码检索与长任务执行。真实模型对照作为并行评估线，依据结果调整后续顺序。继续复用已有 monorepo、双引擎、审批、持久化、恢复、队列和串行工作流，不启动架构重写。

- Claude 持续保持默认。功能替换或评估通过不触发切换，切换由用户另行决定。
- 同时支持 `AGENTS.md` / `CLAUDE.md`；深层优先，同层 AGENTS 优先，用户明确指令优先。新工具沿用既有指令变化检查。
- 功能分支从 `dev/native-agent` 创建，关键修改及时提交，本地验证和复核后仅合入该分支；不修改 main、不发布 Release。
- 日常提交与 PR 不触发 CI。CI、三平台成品构建仅在用户主动要求时执行；本地定向测试按风险运行。
- 规划 PR #44 仅交付文档；后续用户已授权完整执行 N1，其实际验证独立登记。新增开发不隐含授权真实服务预算或 CI。

## 4. 第一批：N1 工程任务闭环

目标：用户能看到正在做什么、为何停住、哪些修改只是实现完成、哪些已有验证；刷新和重启不会把旧状态显示成新进度。

### 4.1 状态与信任边界

实现前在首个 PR 冻结以下契约，具体类型名以评审结果为准：

1. **运行状态**继续使用现有 `RunStatus`，表示执行、取消、失败、预算或恢复结果。
2. **任务进度**记录目标、稳定任务/步骤 ID、顺序、依赖、计划修订、步骤状态和阻塞原因。模型可更新“待办/进行中/已实现”等声明；简单问答无需强制生成计划。
3. **验证状态**单独记录未验证、验证中、通过、失败、不适用或已过期；来源区分宿主工具回执和人工确认。模型文字、工具成功返回、一次无关测试通过均不能自行变成整体验收通过。
4. **证据**引用实际工具调用 ID、命令、工作目录、退出码、日志与截断标志、变更范围及内容指纹；绑定 session/task/run、计划/验收条件修订和相关文件版本。新修改或验收条件变化使相关证据过期；不要只用 HEAD 判断未提交代码是否变化。
5. **展示状态**从宿主权威快照派生，任务计划与证据须先持久化；快照携带会话/run 身份、host epoch、修订和事件序号。持久计划修订与思考/审批/流式等瞬时状态版本分开处理。UI 不从流式文案猜完成，不把断线、等待审批或等待回答误报为执行成功。

验证只证明事先列出的条件在对应代码版本满足。无法自动判定的要求保留人工复核项；不适用必须带理由，旧会话缺少证据时显示“未记录/未验证”，不能补造通过。

### 4.3 队列、工作流与界面约束

- `structured-executor` 的旧 `success` 会影响队列确认、删除已执行消息及工作流推进。**不得用“未验证”直接替换成 `success=false`**，否则已执行消息可能留队并被重发。新增任务验收结果与运行结果并存。
- 默认保留旧工作流语义。用户显式配置验收门槛的新工作流在执行结束后进入独立的“待验证/待确认”，只能显式继续或重试；不回滚队列确认，也不自动重做工具。
- 先复现用户历史反馈的刷新场景，核对现有请求序号与通知合并逻辑，不能预先认定同一缺陷仍然存在。前端订阅使用有序的快照与增量恢复机制；发现序号缺口、连接恢复或窗口重新可见时重新读取快照。终态保存后通知；读取失败显示状态未知及重试入口，不能靠不断轮询制造进度。完成通知与任务面板使用同一完成语义；刷新延迟先测量再确定目标。
- 重启后恢复已保存的计划和证据，但执行中的步骤需按运行记录标记中断/待核查，不能自动续跑未知副作用。旧任务和新回合明确关联，不能让旧回合迟到结果覆盖新任务。
- 任务进度与已有 Claude 子任务追踪并存，不将它包装成已支持 native 多 Agent。

### 4.4 首批验证与完成定义

优先扩展 core/node 的运行与存储测试，desktop 的 `native-projection.test.ts`、`native-worker-host.test.ts`、`native-executor.test.ts`、`chat-queue.test.ts`、`workflows.test.ts`，并为 renderer 的重同步竞态增加定向测试。具体测试文件随实现选用，不为文案修改增加测试。

真实界面需覆盖“启动 → 等待审批/回答 → 修改 → 验证 → 结束”，以及中途刷新、切会话和重启。当前环境没有图形显示，自动化收集/SSR 不能替代 Electron 实际运行；未执行时保留待验收。完成 N1 的代码交付须有本地边界回归、独立复核、文档与迁移说明，图形及真实模型结果分别登记。

## 5. 后续功能批次

### N2：先提高找代码与修改的效率

- **N2-01 文件定位与检索**：文件名/glob、忽略目录规则、有界正则、分页或游标。返回总量是否完整、截断原因、可继续位置和文件身份，避免“没搜到”被误判为不存在。正则需执行时限/复杂度保护，不能只限制输出；搜索沿用项目根、符号链接和指令边界。
- **N2-02 多文件变更预览**：生成任务范围 diff，逐文件校验原始版本，审批对应准确内容；保留用户已有修改。明确冲突及部分应用结果，日志逐项记载。普通文件系统批量写入不冒充跨文件原子事务，失败不盲目回滚或重复执行。
- **N2-03 代码定位体验**：已实现 `record_code_location`，宿主核对完整文件版本与行范围，将历史片段关联任务步骤/条件；[实现记录](NATIVE-AGENT-N2-LOCATIONS.md)区分位置观察和验收结论。正式运行见 RA-25；N2-01 对真实任务的收益仍待 E0 数据。只有字面/正则定位仍成为主要瓶颈时才排 symbol/reference 或 LSP 集成。

验收包含大仓库分页、截断、异常编码、目录/符号链接变化、外部编辑、失败中断和不同平台路径。本地 fixture 验证正确性，E0 记录检索调用数、人工指路次数与越范围修改，不能先宣称效率提升。

### N3：长任务持续执行

- **N3-01 长命令句柄（本地实现完成）**：已提供 `start_command`、`command_status`、`read_command_output`、`stop_command`，限定所属回合内的有限命令；精确审批后由宿主持有句柄，生命周期与终局日志独立持久化并只读展示。启动成功不是命令结束或任务验收；取消/退出等待进程树及句柄清理，清理未知保留隔离。重启未闭合命令显示结果未知，不凭 PID 接管或重启。实现边界与统一验证见 [N3-01 记录](NATIVE-AGENT-N3-COMMANDS.md)，正式运行 RA-26 待执行。
- **N3-02 回合内上下文维护（本地实现完成）**：新增显式选择的“发送前及回合内自动压缩”，默认仍关闭，原发送前模式不变。达到本地预算 90% 时只在完整模型/工具批次边界检查，回合内最多一次摘要，给后续执行保留请求额度。宿主保留原始目标、当前输入、最近完整批次与任务连续性记录；原始日志留存。摘要先持久化再切换，失败或未知不展示成功、不自动重试；摘要计入所属回合用量及同次提交的请求/时间预算。实现边界与本地结果见 [N3-02 记录](NATIVE-AGENT-N3-CONTEXT.md)，正式运行 RA-27 待执行。
- **N3-03 错误诊断与有限恢复（下一步）**：分类认证/配置、限流、暂时服务错误、协议、预算和本地工具错误。只在明确安全边界内按预算退避重试，可取消且次数有界；每次请求可能计费。已准备或结果未知的副作用不重放；部分流响应不能与重试结果拼接。重复失败/无进展触发可解释的阻塞摘要，由用户选择后续。

N3-02 已复用 N3-01 的回合身份、取消、预算和终局事实边界；prepared/running/unknown 长命令暂缓压缩，终态确认后可在后续完整批次重新检查，超出硬预算仍停止。N3-03 的重试策略继续结合二者边界复核。验收覆盖长日志、停止竞态、僵尸进程/后代进程、断流、写盘失败、压缩中取消/崩溃、双协议调用配对和预算耗尽；平台进程树行为需目标平台证据。

### N4：选定服务的能力与连接

围绕 E0 实际服务记录工具调用、上下文、参数、用量及后续图像能力；协议选择继续显式。能力来源和验证时间可见，未知能力不冒充支持。诊断只对用户选定地址执行，不自动试探其他端点。

若选用无认证本地服务，再实现显式 loopback 免密模式；严格核验本地地址及重定向，默认远端仍需既定认证方式，凭据不进入 renderer/日志。对不支持的参数给出明确配置或错误，不按失败静默删除安全相关参数。没有实际服务用例时，不为假定兼容性提前扩张。

## 6. E0：真实工程任务评估线

### 6.1 准备与执行

1. 保留现有三个小任务作为协议/工具 smoke。另为 cc-desk 准备三项固定工程任务：任务状态刷新缺陷、跨 main/IPC/renderer 的小功能、跨包且保持行为的重构。选择可复现缺陷或准备明确注入的评估变体，不把已经修复的问题再当作当前缺陷。
2. 固定任务说明、仓库提交、初始失败、独立验收条件、禁止改动范围与最大预算；验收器及参考实现放在被评估工作区之外。保留原测试和双指令约束，检查新增测试质量，避免只奖励删测试后的绿色结果。
3. 每个引擎从独立干净副本开始，每项至少两轮：三项 × 两个引擎 × 两轮，至少 12 次工程任务运行。先记录当前候选基线，再对改进候选执行同版任务；本地准备、工具开发不等待模型凭据。
4. 实际运行前明确服务、模型、协议、凭据来源、每次/整批预算、审批方式和终止条件；不在文档中保存密钥。使用同一应用候选、任务基线和可比条件；模型/连接不同须披露，不能把模型差异全部归因于执行器。
5. 失败、取消、超预算和服务异常均保留记录，分开标明产品失败与环境阻塞；不能只保留成功重跑。任务或验收规则更新后重新准备同版现场。

### 6.2 指标与预先确定的门槛

| 指标 | 记录方法 / 通过条件 |
| --- | --- |
| 功能正确性 | 独立验收、原测试与任务要求的新测试通过，人工审阅改动属于任务范围；每项至少两轮均符合，才登记该模型/配置的小样本任务通过 |
| 权限与数据完整性 | 未经批准的副作用、身份/项目串用、重放未知结果、丢失用户修改或绕过原测试/指令：出现任何一项即阻断候选验收 |
| 状态可信度 | 实际运行记录与 UI/报告一致；未验证不能显示通过；停止、刷新、重启后无旧状态覆盖或虚假运行 |
| 人工介入 | 分开记录正常审批、任务澄清和为救回任务而提供提示/改代码；后者为零才称无需人工救援完成，不将总审批次数等同失败 |
| 用量/费用/耗时 | 保留服务回执和总耗时；区分模型执行、审批等待和验证时间，记录失败请求/压缩；缺失保持未知，不用部分用量算完整费用 |
| 效率比较 | 记录检索/模型/工具次数、错误循环、人工救援次数；先取得基线，再在下一轮前确定改进目标，不事后挑阈值或以小样本推断通用成功率 |

已有 P5 的每项两轮门槛继续有效，新增工程任务扩大代表性但不能证明所有项目/模型均可替换。工具可以自动输出功能核验结果；真实任务质量仍需独立人工复核，不让模型自评或 `realQualityStatus` 自动冒充认可。

E0-01 材料已固定；[E0-02](NATIVE-AGENT-E0-REPORTS.md)已为 `scripts/native-eval.mjs` 增加独立工程命令，支持固定 12 轮记录、每次验收意图/结果、不可覆盖报告和同版对照，保持旧三任务用法。模型接入具备条件后执行 E0-03 并登记结果。图形和三平台成品验收另列，不因模型任务通过而自动通过。
